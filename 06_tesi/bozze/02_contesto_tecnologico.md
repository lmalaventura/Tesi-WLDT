# Contesto tecnologico — bozza personale

## API REST e specifica OpenAPI

Un'API REST rappresenta un'interfaccia attraverso la quale i vari componenti del sistema possono recuperare o interrogare i dati memorizzati. Ad esempio, il Persistence Service espone le proprie funzionalità agli altri componenti tramite API REST. Ogni operazione viene identificata tramite un metodo HTTP, un path, eventuali path parameter o query parameter e un eventuale request body; perciò ogni chiamata prodotta deve corrispondere ad una operazione possibile e strutturalmente coerente con il sistema. L'interfaccia API REST è descritta formalmente attraverso la specifica OpenAPI, che rappresenta un contratto in cui vengono definite le operazioni disponibili e come devono essere utilizzate. All'interno di questo progetto viene utilizzata come modello paradigmatico per impedire che l'agente sviluppato lavori su endpoint non definiti o non aggiornati. Come accennato in precedenza, il recupero della specifica avviene in maniera dinamica dall'indirizzo configurato, trasformando poi le informazioni ottenute in un catalogo normalizzato, più compatto rispetto al documento originale. Il catalogo normalizzato ottenuto verrà poi utilizzato in una selezione preliminare delle operazioni maggiormente compatibili rispetto alla richiesta dell'utente.

## Large Language Model e inferenza locale

In questo progetto viene utilizzato un Large Language Model nell'interpretazione della richiesta dell'utente, andando poi a trasformarla in una rappresentazione strutturata della chiamata REST da eseguire. L'impiego del LLM è stato pensato in un dominio ristretto e specifico, ricevendo un prompt contenente un insieme limitato di operazioni, precedentemente selezionate dall'Agent Service.
L'inferenza viene eseguita localmente tramite Ollama, un software open-source che permette la gestione di modelli linguistici in locale. La possibilità di utilizzare il modello Qwen3 8B localmente, quindi eliminando un'ipotetica dipendenza da un servizio cloud, permette un maggiore controllo dell'ambiente di sperimentazione. Inoltre Ollama restituisce alcune metriche generative, come il numero di token elaborati, token prodotti e durata complessiva dell'inferenza, risultate utili in fase di confronto tra i vari modelli presi in esame.
La risposta richiesta è un oggetto JSON, la cui struttura contiene metodo HTTP, endpoint, parametri, request body ed eventuali 'missingInformation', facilitando l'elaborazione della risposta. Tuttavia risulta comunque necessaria una validazione semantica della chiamata rispetto all'operazione selezionata, in quanto non viene autonomamente garantita dall'elaborazione della risposta.

## Agent Service, FastAPI e comunicazione HTTP

Lo sviluppo ha seguito una logica di independenza di un Agent Service rispetto agli altri componenti WLDT, cosicchè la gestione del modello linguistico rimanga esterna, adattando quindi il nuovo servizio alle interfacce già offerte dal Persistence Service. Questa soluzione ha perciò portato a una complessità interna dell'Agent Service indipendente e non trasferita nel frontend o nel backend del ambiente in cui si posiziona.
L'implementazione dell'agente avviene attraverso FastAPI in Python. Il framework utilizzato permette di esporre endpoint HTTP, una definizione di modelli di input e output e una generazione automatica di una documentazione interattiva tramite Swagger. La ricezione del testo dell'utente e il coordinamento delle diverse fasi della pipeline avviene grazie all'endpoint principale POST /query.
Le comunicazioni HTTP vengono gestite attraverso la libreria httpx, utilizzata in modalità asincrona per permettere che l'elaborazione non venga bloccata inutilmente durante l'attesa delle risposte esterne. 
La validazione e la descrizione delle strutture dei dati scambiati vengono definite dalla libreria Python Pydantic, permettendo la verifica delle richieste ricevute dall'Agent Service e la verifica della struttura generale della chiamata prodotta dal modello.
